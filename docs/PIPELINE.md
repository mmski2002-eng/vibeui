# PIPELINE

Как item попадает в каталог. Это про конвейер, не про ассортимент: что и в
каком порядке делать — [ASSORTMENT.md](ASSORTMENT.md).

## Единственный ручной источник

Руками правятся только:

- `registry/<blocks|components>/<category>/registry.json` — metadata;
- `registry/<...>/<name>/<name>.tsx` — сам компонент;
- `registry/categories.ts` — когда заводится новая категория.

Всё остальное генерируется `npm run indexes` из этих файлов:

| файл                        | что в нём                                 |
| --------------------------- | ----------------------------------------- |
| `registry/sources.ts`       | список реестров и `kind` каждого          |
| `registry/previews.ts`      | карта slug → компонент для миниатюр и SSR |
| `registry/previews.lazy.ts` | ленивая карта для конфигуратора           |
| `registry.json` (корневой)  | `include[]` публикуемых реестров          |

Генератор — `scripts/build-indexes.mjs`. Он же проверяет инварианты, которые
раньше держались договорённостью: категория объявлена в `categories.ts`,
`categories[0]` item'а совпадает с реестром, `meta.ai.export` совпадает с
именем экспорта, выведенным из slug.

Зачем: раньше один item требовал правок в трёх параллельных индексах, а новая
категория — в пяти файлах. Это блокировало параллельную работу: два item'а
трогали одни и те же строки. Теперь папки item'ов независимы.

Порядок в каталоге: сначала блоки, потом компоненты; внутри типа — порядок
категорий из `registry/categories.ts`. Двигать item в каталоге = двигать его
категорию там.

## Новый item

```bash
npm run item -- <категория> [префикс]   # npm run item -- inputs input
```

Скаффолд заводит папку, `.tsx` по эталону (своя палитра `--vibeui-<name>-*`,
`<style href precedence>`, `prefers-reduced-motion`) и заготовку metadata с
`TODO`, после чего пересобирает индексы.

Заготовка намеренно **не проходит** `npm run meta:validate`: пока в metadata
остались `TODO`, сборка падает. Незаполненный item не уезжает на витрину.

Дальше по item'у:

1. написать компонент — визуальная идея, а не вариация цвета соседа;
2. заполнить metadata: `title`, `description`, `tags`, `ai.summary`,
   `ai.preserve` / `ai.adapt` (минимум по три пункта), `ai.notes`, `docs`;
3. для `kind: component` — `ai.usage` и `meta.controls`;
4. перевести: `meta.i18n.en` с тем же числом пунктов в списках;
5. `npm run meta:validate && npm run lint && npm run build`;
6. глазами: `/preview/<name>`, карточка в каталоге, страница item'а,
   светлая и тёмная подложка превью.

## Два правила, которые ловятся только сборкой

**Item обязан рендериться без пропсов.** Карта превью типизирована как
`Record<string, ComponentType>`, поэтому обязательный проп роняет `typecheck`.
Практический смысл тот же: миниатюра каталога рендерит компонент пустым, и
у него должно быть осмысленное состояние по умолчанию.

**Подложка превью объявляется в metadata.** `meta.preview.surface` (`"dark"`
или `"light"`) говорит, на каком фоне открывать карточку и страницу item'а.
Это не тема компонента — свою палитру он несёт сам и от контекста не
перекрашивается; поле лишь не даёт открыть светлое поле формы на тёмной
подложке. Пользователь всё равно может переключить.

Там же `meta.preview.width`: `auto` — компонент занимает столько, сколько
просит (кнопка, плашка, аватар), `full` — ему нужна настоящая ширина строки
(поле формы, карточка, полоса прогресса). Кадр превью центрирует содержимое
флексом, поэтому без `full` такой компонент схлопнется по содержимому и
покажет не тот дизайн, который получит пользователь.

И `meta.preview.props` — пропсы только для витрины. Миниатюра рендерит
компонент без аргументов, поэтому состояние, которое видно лишь по наведению
(подсказка) или через конфигуратор, на карточке не покажется. В устанавливаемый
файл это не попадает и дефолты компонента не меняет.

## Перед новым item — соседние категории

Категории режут по устройству компонента, а сценарии живут поперёк. Слот
записи лежит и в «Календаре», и в «Календаре событий»; мини-календарь с
точками — там же; сегмент с бегунком есть и в «Группе кнопок», и в «Группе
переключателей». Поэтому перед тем, как заводить item, ищут по всему
каталогу, а не по своей папке:

```bash
grep -rl "<ключевое слово сценария>" registry/*/*/registry.json
npm run audit            # заодно покажет, что каталог здоров
```

Дубль между категориями хуже дубля внутри: внутри его видно при первом же
взгляде на список, а между — нет, и он живёт годами. Два таких пришлось
удалить уже после того, как они были написаны, проверены и отправлены.

## Витринный режим у всего, что открывается

Компонент, содержимое которого спрятано до нажатия — меню на HTML popover,
модальное окно, панель, лист снизу, — на карточке каталога показывает **одну
кнопку**. Человек листает витрину и видит ряд одинаковых кнопок вместо
дизайна, за которым пришёл. Поэтому у каждого такого компонента есть prop
`open` (у панелей на `<dialog>` — `defaultOpen`), который раскрывает
содержимое **в потоке страницы**, а не в верхнем слое:

```tsx
popover={open ? undefined : "auto"}
data-open={open || undefined}
```

```css
/* Меню: кнопка остаётся, меню встаёт под ней. */
[data-vibeui-block="имя"]:has([data-open="true"]){flex-direction:column;align-items:flex-start}
[data-vibeui-имя-menu][data-open="true"]{position:static;opacity:1;transform:none;margin-block-start:0.375rem}

/* Окно: кнопка прячется, окно занимает её место. */
[data-vibeui-block="имя"]:has([data-open="true"]) [data-part="trigger"]{display:none}
[data-vibeui-имя-window][data-open="true"]{position:static;inset:auto;margin:0;opacity:1;transform:none}
```

В этом режиме popover не используется, поэтому Esc и клик мимо не работают —
он для витрины, скриншотов и отладки, а не для страницы пользователя. Сам
prop в `meta.controls` не заводят: это не настройка компонента. В metadata
достаточно `meta.preview.props: { "open": true }` и той же строки в
`meta.i18n.en.preview.props`.

`npm run audit` ловит и обратное — компонент с popover без такого режима.

## Сплошная проверка витрины

Статический аудит не видит того, что случается при рендере: блок вылезает за
кадр и тянет горизонтальную прокрутку страницы. Это ловится только браузером,
и проверять стоит весь каталог разом, а не по одному item'у.

Приём: собрать список всех items из `registry/*/*/registry.json`, открыть
`/preview/<kind>/<категория>/<имя>` в кадре шириной 320px (восемь кадров
параллельно — полторы тысячи items проходят примерно за двадцать минут) и на
каждом посчитать `document.documentElement.scrollWidth - clientWidth`. Всё,
что больше нуля, — дефект: на телефоне такой компонент разъезжает страницу.

Проверять стоит обе границы: 320px (iPhone SE, самый узкий поддерживаемый) и
420px. На 420 проходят почти все, на 320 вылезает вдвое больше — узкая
граница и есть настоящая проверка.

Что НЕ считать дефектом: маленькую высоту. Хлебные крошки, бейдж, разделитель
и аватар законно занимают 18–40px, и порог по высоте даёт только ложные
срабатывания. Прокрутка ВНУТРИ блока — у таблицы, у ленты, у плана работ —
тоже норма, если она объявлена своим `overflow-x:auto`.

Частые причины настоящей прокрутки: grid- или flex-элемент без
`min-inline-size:0` (по умолчанию `min-width:auto` не даёт ему сжаться),
`<input>` со своей шириной по умолчанию, панель фиксированной ширины больше
кадра, всплывающая часть, позиционированная вправо от блока.

Контраст в тёмной теме так проверить НЕ выходит. Считать его по DOM —
`getComputedStyle().color` против фона ближайшего предка — бесполезно: фон
под текстом часто рисует не предок, а соседний слой (плашка сегмента под
кнопкой, псевдоэлемент, градиент), и замер уверенно сообщает про белый текст
на белом там, где глазами всё читается. Полтора десятка таких «находок»
оказались ложными все до одной. Тёмную тему проверяют глазами по
`?theme=dark`, а автоматике оставляют то, что она умеет мерить честно, —
геометрию.

## Ловушка контейнерных запросов

`@container` применяется к **потомкам** контейнера, но не к самому контейнеру.
Правило вида

```css
@container (max-width: 26rem) {
  [data-vibeui-block="alert-001"] {
    flex-wrap: wrap;
  } /* молча не работает */
}
```

не срабатывает никогда: элемент с `container-type` не может отвечать на
собственный запрос. Внешне это выглядит как «адаптив не включился»: на узкой
ширине раскладка остаётся прежней, а соседний потомок сжимает текст до нуля.

Что делать: свойства корня задавать в базовом правиле (`flex-wrap:wrap` не
мешает на широкой раскладке — там всё умещается в строку), а внутри
`@container` менять только потомков — базисы, отступы, кегль. Если корню нужен
адаптивный `padding`, заводится внутренний `[data-part="frame"]`, как в блоках.

`meta:validate` проверяет это и роняет сборку.

## Что проверяет `meta:validate`

`scripts/validate-meta.mjs` знает про наши поля, которых нет в схеме shadcn.
Ошибки роняют сборку.

Metadata:

- остались `TODO` из скаффолда;
- нет `title`, `description` короче 40 символов, пустые `tags`;
- нет `ai.summary`, меньше трёх пунктов в `ai.preserve` / `ai.adapt`;
- нет `i18n.en`, в переводе не совпало число пунктов списка, не переведён
  `usage`, у контрола нет английского `label`, у текстового — `default`;
- контролы: дубли, неизвестный тип, `default` вне `options` или длиннее
  `maxLength`, цвет не `#rrggbb`;
- `preview.states`: не массив, меньше двух или больше четырёх наборов,
  элемент не объект;
- для `kind: component` — нет `ai.export`, нет ни `usage`, ни `controls`.

Исходник item'а:

- нет экспорта с ожидаемым именем (`button-001` → `Button001`);
- импорт откуда-либо кроме `react` — item обязан быть самодостаточным;
- классы темы проекта-хозяина (`bg-primary`, `text-muted-foreground` и т.п.):
  компонент несёт свою палитру, иначе после установки выглядит не так,
  как в preview;
- CSS-переменная без префикса `--vibeui-`;
- есть анимация, но нет правила `prefers-reduced-motion`;
- внутри `@container` есть правило для самого блока — оно не работает.

Предупреждения не роняют сборку: связь контрола с `ai.adapt` ищется по тексту
и даёт ложные срабатывания.

## Витрина: демо-данные, фотографии и ряд состояний

Всё, что относится к показу item'а на сайте, живёт в `meta.preview` и в
устанавливаемый файл не попадает. Перед публикацией `scripts/strip-preview.mjs`
вырезает этот блок из `public/r/*.json`: агент читает JSON целиком и подставил
бы наши демо-пути в чужой проект, где их нет.

- `preview.width` — `auto` или `full`, нужна ли компоненту настоящая ширина
  строки;
- `preview.props` — пропсы только для кадра витрины: фотографии, демо-текст;
- `preview.states` — от двух до четырёх наборов пропсов. Миниатюра каталога
  рендерит компонент по разу на каждый набор в горизонтальный ряд, поэтому
  мелкий компонент не стоит в пустом кадре, а размеры и состояния видно с
  витрины. Высота карточки при этом не меняется. Как только человек трогает
  настройку, ряд уступает место одному настроенному экземпляру, и сниппет
  «Копировать для ИИ» по-прежнему описывает **один** компонент.
- `i18n.en.preview.props` — то же для английской витрины. Русские подписи
  внутри компонента — это его дефолты, и на `/en` их перекрывает только этот
  блок. Забыть его — значит показать англоязычному человеку «Установок» и
  «В команде».

### Демо-фотографии

`public/demo/avatars/` — шесть портретов, `-256` для обычных кадров и `-512`
для крупных (загрузка фото, редактор, шапка профиля). Снимки **синтетические**,
сгенерированы нейросетью специально для витрины: это не сток и не реальные
люди, лицензия и права на изображение здесь ни при чём.

Имена в демо-данных категории берутся из одного набора, и фотография следует за
именем: подписать лицо одного человека именем другого — самый заметный способ
показать, что демо собрано наспех.

## Ревизия готовой категории

Отдельная работа: не «завести item», а пройти категорию целиком и довести её
до состояния, в котором её не стыдно показывать. Порядок — ниже; проверено на
аватарах, автодополнении и баннерах.

### 1. Анализ до правок

Прочитать код всех items категории и посмотреть их глазами. Сверить с тем, что
делают зрелые библиотеки и живые продукты. Выписать: что устарело, что
дублируется, каких сценариев нет.

Дубли сливать в один item с настройкой, а не держать двумя карточками.
Мёртвое удалять — в аватарах ушло шесть items.

### 2. Пробелы в покрытии

Выписать реальные сценарии категории и отметить закрытые. Недостающие
дописать, и это должен быть другой сценарий, а не вариация цвета соседа:
стопка баннеров, отсчёт акции, согласие с категориями, архивная версия;
мультивыбор, ошибка с повтором, двухпанельный поиск; кроппер фотографии,
генеративный identicon, шапка профиля.

### 3. Проверка каждого файла

Тема. `light-dark()` смотрит только на `color-scheme`, а shadcn и next-themes
переключают класс. Без строки

```css
:where(.dark, [data-theme="dark"]) [data-vibeui-block="name-001"] {
  color-scheme: dark;
}
```

компонент останется светлым на тёмной странице чужого проекта.

Акцент. Пользовательский цвет приходит один на обе ветки темы, поэтому текст
на заливке выводится из его светлоты:
`oklch(from var(--accent) clamp(0,(0.62 - l) * 100,1) 0 0)`. Фиксированный
белый однажды окажется белым на жёлтом.

Приглушённый текст — `color-mix(in oklab,var(--fg) 68%,transparent)`, а не
фиксированный серый: на цветной подложке серый тонет.

Цвет задаётся каждой текстовой части. Без этого имя на светлой карточке
приходит белым со страницы-хозяина.

`container-type` отрывает ширину от содержимого: без
`min-width:min(100%,16rem)` компонент схлопывается в пару пикселей внутри
flex-кадра. Про сам `@container` — раздел «Ловушка контейнерных запросов».

Доступность: landmark-роли, `<time dateTime>`, настоящий `input type="checkbox"`
вместо ролей, `aria-expanded` и `aria-controls` у раскрывающегося,
`:focus-visible` у всего интерактивного. `aria-live` — там, где состояние
меняется само, но не на отсчёте по секундам: это превращает полосу в
непрерывную речь. Свёрнутые строки оставлять в разметке под `hidden` —
счётчик «ещё 2» не рассказывает скринридеру, что именно скрыто.

### 4. Геометрия

Последний прогон и самый урожайный: эти дефекты не видны, пока не начнёшь
мерить.

- фиксированная `height` у кнопки — длинная подпись переносится на вторую
  строку и выходит за пределы кнопки; всегда `min-height` с вертикальным
  padding;
- `width:100%` вместе с `margin-left` — выход за правый край ровно на
  отступ; `calc(100% - отступ)`;
- `flex:1` на трёх кнопках в узком контейнере — обрезанный текст;
  `flex:1 1 100%`, каждая на своей строке;
- `min-width` из базового правила переживает узкую ветку `@container` и снова
  ломает ширину — сбрасывать в нуль;
- крестик после переноса кнопки на всю ширину уезжает отдельной строкой —
  уводить абсолютом в угол;
- вырезы под бейдж (`mask-image`): центр выреза совпадает с центром бейджа,
  радиус — радиус бейджа плюс 2 px, для квадратного `* 0.707 + 2px`;
  несколько вырезов — `mask-composite:intersect`.

Метод. Прогнать все items категории в `iframe` на ширинах 260, 300, 360, 420,
520, 700, 900, 1100 и померить у каждой кнопки, ссылки, поля и подписи
`scrollWidth - clientWidth`, `scrollHeight - clientHeight` и выход за границы
блока. Раскрывающиеся состояния — сначала кликнуть, потом мерить: у свёрнутой
панели половина разметки просто отсутствует.

### 5. Настройки

Целевое — три-пять настроек на item: лишние резать, недостающие вариации
добавлять. У каждой настройки значок в шапке карточки, у текста и цвета —
выпадающее поле с подписью, что меняем, у цвета — кнопка «Цвет темы».
Схема и значки — [CONTROLS.md](CONTROLS.md).

### 6. Проверка результата

`npm run meta:validate`, `npm run lint`, `npm run build` — зелёные.

Прогон категории в «Рабочей области» (`/lab`) дважды: на дефолтах и на
случайных настройках. Второй прогон находит то, чего на дефолтах нет — там
всплыли утонувший приглушённый текст и имя, наследующее цвет страницы.

Глазами: `/preview/<name>`, карточка каталога, страница item'а, обе подложки
превью, обе ветки темы, mobile / tablet / desktop.

## Параллельная работа

Item'ы независимы, кроме одного общего файла — `registry.json` своей
категории. Отсюда правило: **параллелить можно item'ы разных категорий**;
внутри одной категории — последовательно или с ручным разрешением конфликта
в конце (конфликт всегда один и тот же: два добавленных элемента `items[]`).

Индексы не коммитятся вручную: после слияния достаточно `npm run indexes`.

## Команды

```bash
npm run item -- <категория>   # скаффолд item'а
npm run indexes               # пересобрать индексы
npm run indexes:check         # упасть, если индексы устарели (CI)
npm run meta:validate         # metadata и исходники item'ов
npm run registry:build        # shadcn build + вырезание витринных данных
npm run build                 # indexes + meta:validate + registry:build + next build
```
