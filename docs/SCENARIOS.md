# SCENARIOS — вход в каталог со стороны задачи

## Зачем

«Компоненты / Блоки / Анимации» описывают, **из чего собрана библиотека**.
Человек приходит с другим: «делаю сайт мастера», «нужен магазин», «собираю
личный кабинет». Между его задачей и нашей таксономией — пропасть: отличить
«Поле с подсказками» от «Автодополнения» на входе невозможно, да и не нужно.

Сценарий закрывает эту пропасть: берёт задачу и раскладывает её в
упорядоченный список секций, называя каждую **ролью на странице**, а не
именем категории. «Форма заявки», а не «Контакты».

Категории при этом никуда не деваются — сценарий просто другой вход в них.

## Чем сценарий не является

`registry/categories.ts` объявляет `kind: "template"` — «Шаблоны». Это
готовая страница **одним item'ом**, которая устанавливается целиком.

Сценарий — не шаблон. Он ничего не устанавливает и не публикуется в
реестре: это маршрут по уже существующим блокам. Ставятся сами блоки,
своими обычными командами.

## Где что лежит

| Файл                                                       | Что                                                 |
| ---------------------------------------------------------- | --------------------------------------------------- |
| `registry/scenarios.ts`                                    | данные: сценарии, шаги, роли, обложки               |
| `lib/scenario.ts`                                          | резолв шагов из живого каталога и промпт для агента |
| `app/scenarios/page.tsx`, `app/scenarios/[slug]/page.tsx`  | витрина и страница сценария (плюс `/en`)            |
| `components/pages/scenarios-page.tsx`, `scenario-page.tsx` | разметка                                            |

Данные — единственное в каталоге, что **нельзя вывести из registry**: «что с
чем сочетается и в каком порядке» — решение автора, а не свойство файлов.
Поэтому список ведётся руками.

Всё остальное берётся из живого каталога: какие именно items показать в
шаге, сколько их всего, что поставить по умолчанию. Поэтому сценарии не
устаревают, когда блоки добавляются или удаляются.

## Устройство сценария

```ts
{
  slug: "store",
  label: "Магазин",
  en: "Store",
  summary: "Витрина товаров, карточка и оформление заказа",
  summaryEn: "…",
  steps: [
    {
      category: "commerce",              // слаг из registry/categories.ts
      role: "Витрина и карточка товара", // роль на странице, не имя категории
      roleEn: "Showcase and product page",
      why: "Сетка товаров, карточка, корзина, оформление",
      whyEn: "…",
      optional: true,                    // страница живёт и без этой секции
    },
  ],
  cover: "commerce",   // чей блок показывать обложкой на витрине
  parts: ["button", "badge", "rating"],  // мелкие компоненты
}
```

`cover` задаётся явно и намеренно: первым шагом почти везде идёт «шапка», и
без этого поля половина карточек на витрине выглядела одинаково.

Слаги проверяются при загрузке модуля — опечатка роняет сборку, а не
оставляет пустой шаг на витрине.

## Как работает страница

1. Шаг показывает роль, пояснение «зачем» и до четырёх вариантов с живым
   превью — тем же компонентом из `registry/`, что и в каталоге.
2. Первый вариант выбран по умолчанию: `featured` вперёд, дальше порядок
   каталога. Новичку не надо выбирать вслепую.
3. Клик по «Выбрать» кладёт выбор в адрес (`?hero=hero-004`), поэтому
   собранным сценарием можно поделиться ссылкой — как со значениями
   контролов на странице item'а.
4. Кнопка **«Копировать сценарий для ИИ»** собирает один промпт: порядок
   секций, выбранные блоки, команды установки и правила. Это главное отличие
   от `Copy for AI` одного item'а — там компонент, здесь целая страница.

Кадр превью не оборачивается ссылкой: внутри живой блок со своими ссылками,
а `<a>` внутри `<a>` — ошибка разметки и сломанная гидратация. Выбор делает
строка под кадром.

## Что делать при новой категории

Сценарии — ручные данные, и они не узнают о новой категории сами. Если
категория попадает в типовую страницу, добавьте её шагом в подходящий
сценарий: слаг, роль, «зачем», перевод. Если не попадает — ничего делать не
нужно.

Если категория тонкая (два-три items), сценарий это обнажит: в шаге будет
нечего выбирать. Это полезный сигнал, куда пополнять каталог, а не повод
убирать шаг.

## Чего делать нельзя

- **Публиковать сценарий в реестре.** Он не item: ставить нечего.
- **Хардкодить конкретные items в данных сценария.** Шаги ссылаются на
  категории; конкретика приезжает из каталога, иначе сценарий рассыпется
  при первом же удалении блока.
- **Называть шаг именем категории.** Роль на странице — половина ценности
  сценария: именно она объясняет человеку, что он выбирает.
