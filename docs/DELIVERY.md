# DELIVERY — Product Delivery Model v1

Как компонент попадает от каталога к пользователю. Этот документ важнее
developer UX: VibeUI не библиотека для программистов, а инструмент для
вайбкодеров, которые часто не пишут код вообще.

Целевое действие пользователя — не «скопировать код», а сказать агенту:
«размести вот такую кнопку тут».

## Главный артефакт — ссылка

Артефакт ровно один. Не комбинация и не «на выбор».

| Артефакт                       | Роль                                                                    | Кому             |
| ------------------------------ | ----------------------------------------------------------------------- | ---------------- |
| **Ссылка `/c/<name>`**         | Продукт. Пользователь вставляет её в собственную фразу агенту           | Всем. Это дефолт |
| Полная инструкция              | Запасной путь: копируется целиком, если агент не может открыть ссылку   | Меньшинству      |
| Registry URL / install command | Транспорт. Живёт внутри инструкции; наружу вынесен для работающих с CLI | Меньшинству      |
| Исходник                       | Доверие и правка руками. **Не путь установки**                          | Программистам    |

Правило, из которого выводится вся выдача:

**Пользователь не должен выбирать между кодом, registry URL и инструкцией.**

Одно очевидное действие, всё остальное — глубже. Три равнозначные кнопки
подталкивают к «скопируй код», а это ломает главное обещание: агент должен
установить настоящий компонент из registry, а не пересоздать похожий.

Почему ссылка, а не текст промпта. Промпт вырос до 3000–5000 символов, и
вставлять его в чат неудобно: он вытесняет собственную фразу пользователя,
а строку «куда поставить» приходится дописывать внутри стены текста.
Ссылка занимает ~45 символов и встраивается в обычное предложение:

```
размести такую кнопку в шапке: https://vibeui.ru/c/button-001
```

shadcn-совместимый registry остаётся механикой установки. Меняется не он,
а то, что видит пользователь.

### Почему по ссылке нет исходника

`/c/<name>` отдаёт ~1000 символов plain text: команда установки, путь,
экспорт, сниппет использования и три главных правила. Кода компонента там
нет **намеренно**.

Если бы он там был, агент с большой вероятностью перепечатал бы его сам
вместо запуска команды, а перепечатанный моделью код — уже не тот же файл.
Фидельность держится отсутствием альтернативы, а не уговорами в тексте:
копировать нечего, поэтому единственный способ выполнить инструкцию —
запустить `npx shadcn add`.

Второе следствие короткого документа: он проходит фетч агента без искажений.
Чем меньше текста, тем меньше шансов, что он приедет пересказанным.

## Карточка каталога

Кадр превью в рамке и узкая строка под ним: имя слева, одно действие справа.

- **Copy for AI** — копирует ссылку `/c/<name>`, не текст промпта;
- имя item'а — растянутая ссылка на страницу item'а.

Registry URL и View code с карточки убраны — на витрине они конкурировали
с главным сценарием. Оба остались на странице item'а.

После копирования кнопка говорит **«Ссылка скопирована»**.

В правом верхнем углу кадра — переключатель светлой и тёмной подложки
превью. Состояние локальное для карточки. Переключается **только подложка**:
сами блоки и компоненты theme-independent, оболочка каталога не имеет права
их перекрашивать.

Технически: над растянутой ссылкой поднимаются только кнопки (`z-10`) —
Copy for AI и переключатель темы. Второй ссылки на тот же адрес в разметке
нет: внутри превью есть собственные `<a>`, а вложенные ссылки невалидны.

## Страница item'а

Порядок сверху вниз = порядок убывания важности:

1. **Preview** — пользователь проверяет глазами, что это то самое;
2. **«Использовать с AI»** — главный блок: три шага прописью, пример готовой
   фразы со ссылкой, большая кнопка Copy for AI, свёрнутая полная
   инструкция. Выделен усиленной рамкой;
3. **«Для разработчика»** — install-команда, registry URL, свёрнутый исходник.
   Мелким заголовком, визуально вторично.

Три шага: скопируйте ссылку → напишите агенту своими словами и вставьте её
в предложение → агент откроет ссылку и поставит компонент. Куда поставить,
пользователь говорит собственными словами в собственной фразе — отдельного
слота размещения больше не нужно.

Свёрнуто по умолчанию: полная инструкция, исходник. Оба нужны для доверия
(«покажи, что ты мне подсовываешь»), но не должны отбирать экран у действия.

## Бриф по ссылке — `/c/<name>` (реализовано)

Генератор — `buildAgentBrief()` в `lib/copy-for-ai.ts`, маршрут —
`app/c/[slug]/route.ts`, `text/plain`, пререндерится для всех items.
Собирается из той же `meta.ai`, вручную ничего не дописывается.

Состав: имя и описание · команда установки с явным запретом писать код
самому · путь установки · экспорт · npm-зависимости · сниппет из
`meta.ai.usage` · **первые три** пункта `meta.ai.preserve` · строка по `kind`
о размещении · ссылка на страницу компонента.

Обрезка до трёх правил намеренна: остальное агент прочитает в файле, который
к этому моменту уже установлен. Объём — 800–1200 символов против 3000–5000
у полной инструкции.

Контракт: `buildAgentBrief(item, { installCommand, registryUrl, kind, pageUrl })`.

### Проверено установкой

Чистый проект (только `package.json`, `tsconfig.json`, `components.json`,
пустые `app/` и `components/`), команда из брифа:

- CLI создал `components/vibeui/button-001.tsx`;
- SHA-256 установленного файла совпал с исходником в `registry/` —
  байт в байт;
- агент, получивший фразу «размести такую кнопку в шапке: `/c/button-001`»,
  сначала выполнил установку, затем импортировал `Button001` из
  установленного пути и поставил его внутрь `<header>` с пропсами из
  сниппета. Свой вариант кнопки не писал.

Не проверено: поведение конкретно `WebFetch` на боевом домене. Локальный
тест шёл по `http://localhost`, а он до `https` не апгрейдится — это
достаётся первому тесту после деплоя.

## Полная инструкция — запасной путь (реализовано)

Генератор — `buildCopyForAiPrompt()` там же. Восемь секций:

1. **Install first — do not skip, do not recreate** — команда, registry URL,
   `Installs to` из `files[0].target`, npm- и registry-зависимости и явный
   запрет пересоздавать / подменять / переписывать под стиль проекта;
2. **What it is** — `description` + `meta.ai.summary`;
3. **How to use it** — строка импорта и сниппет, если есть `meta.ai.export`
   и `meta.ai.usage`; иначе — объяснение по `kind` и указание прочитать
   установленный файл;
4. **Where to place it** — текст по `kind` + строка `Placement: ___`;
5. **Keep exactly as installed** — `meta.ai.preserve`;
6. **You may change** — `meta.ai.adapt`;
7. **Rules** — `meta.ai.notes`;
8. **Verify** — рендерится, нет ошибок в консоли, совпадает с preview;
   если нет — тронуто что-то из секции 5.

Секции 3 и 4 — то, чем выдача мелкого компонента отличается от выдачи
секции. Блок ставится один раз как секция страницы и не должен попадать
внутрь узкого inline-контейнера; компонент ставится ровно туда, куда
попросил пользователь, и заменяет собой существующий контрол, а не
добавляется вторым.

Строка `Placement: ___` — v1-форма слота размещения. Пользователь дописывает
её своими словами уже в чате агента; если строка осталась пустой, промпт
велит агенту спросить, а не угадывать. UI-пикера сценариев в v1 нет.

Контракт генератора: `buildCopyForAiPrompt(item, { installCommand,
registryUrl, kind })`. `kind` приходит от вызывающего (`getItemKind`),
поэтому сам генератор не зависит от реестра.

### export и usage

Два авторских поля в `meta.ai`, оба опциональны в типе:

| Поле     | block       | component                 |
| -------- | ----------- | ------------------------- |
| `export` | опционально | обязательно по соглашению |
| `usage`  | опционально | обязательно по соглашению |

Типом это не выражено намеренно: иначе пришлось бы прямо сейчас
переписывать metadata всех пяти существующих блоков. Для секции агент и
без сниппета справится — она ставится целиком, и генератор явно велит
прочитать установленный файл. Для мелкого компонента без `usage` агент не
знает, с какими пропсами его вставлять, поэтому у первого же
`registry/components/*` эти поля обязаны быть заполнены.

Список пропсов **не хранить**: он в установленном файле, агент его прочитает.
Дублировать значит гарантировать дрейф.

Всё остальное выводимое и в `registry.json` не пишется: install-команда
(`REGISTRY_BASE_URL` + `name`), путь установки и импорта (`files[0].target`),
`kind` и `group` (реестр и категория), секции «Where to place it» и «Verify».

Общая инструкция «установи из registry, не пересоздавай» живёт **только**
в секции 1 генератора. Из `meta.ai.notes` всех пяти блоков одноимённая
строка удалена: она была скопирована в каждый item и дублировала то, что
промпт теперь говорит сам.

## Режимы превью (реализовано)

Превью выбирается по `kind` — это было условием того, чтобы мелкие
компоненты вообще можно было показывать: секционный масштаб `≈0.26`
превратил бы кнопку в нечитаемую точку около 40px.

| Место                    | `kind: block`                              | `kind: component`                          |
| ------------------------ | ------------------------------------------ | ------------------------------------------ |
| Миниатюра карточки       | рендер в 1280px + `.block-thumbnail-scale` | натуральная величина, центр кадра, паддинг |
| Фрейм на странице item'а | 760px                                      | 320px                                      |

Кадр блока держит пропорцию 16/9 — она равна пропорции секции в 1280×720,
поэтому блок заполняет кадр без полос и обрезки. Кадр компонента пропорции
не имеет: `min-h-44` и рост под содержимое. Сетка не прыгает, потому что
блоки и компоненты живут на разных маршрутах (`/blocks` и `/components`).

`/preview/[slug]` центрирует компонент и оставляет секцию как была. Решает
`components/catalog/catalog-thumbnail.tsx` (kind берётся из `getItemKind`),
`compact` у `BlockPreview` и ветка в `app/preview/[slug]`.

Подложка кадра по умолчанию **тёмная**, заодно с оболочкой каталога;
переключателем меняется на светлую. Переключается только подложка
(`--preview-surface`), сам компонент не перекрашивается.

Плата за тёмный дефолт известна: `button-004` (тихая) и `button-011`
(ссылка) рассчитаны на светлую поверхность — их подпись `oklch(0.45)` на
тёмном фоне читается плохо. Пока это лечится переключателем; по-настоящему
закроется, только когда у компонентов появится тёмный вариант палитры
(`prefers-color-scheme` или собственный data-атрибут).
