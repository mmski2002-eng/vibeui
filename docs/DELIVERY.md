# DELIVERY — Product Delivery Model v1

Как компонент попадает от каталога к пользователю. Этот документ важнее
developer UX: VibeUI не библиотека для программистов, а инструмент для
вайбкодеров, которые часто не пишут код вообще.

Целевое действие пользователя — не «скопировать код», а сказать агенту:
«размести вот такую кнопку тут».

## Главный артефакт — промпт

Артефакт ровно один. Не комбинация и не «на выбор».

| Артефакт                       | Роль                                                                            | Кому             |
| ------------------------------ | ------------------------------------------------------------------------------- | ---------------- |
| **Copy for AI prompt**         | Продукт. Внутри него уже есть команда установки, зависимости и правила          | Всем. Это дефолт |
| Registry URL / install command | Транспорт. Живёт внутри промпта; наружу вынесен для тех, кто сам работает с CLI | Меньшинству      |
| Исходник                       | Доверие и правка руками. **Не путь установки**                                  | Программистам    |

Правило, из которого выводится вся выдача:

**Пользователь не должен выбирать между кодом, registry URL и промптом.**

Одно очевидное действие, всё остальное — глубже. Три равнозначные кнопки
подталкивают к «скопируй код», а это ломает главное обещание: агент должен
установить настоящий компонент из registry, а не пересоздать похожий.

shadcn-совместимый registry остаётся механикой установки. Меняется не он,
а то, что видит пользователь.

## Карточка каталога

Ровно одно действие:

- **Copy for AI** — primary-кнопка, доминирует;
- «Подробнее» — приглушённый текст справа, ведёт на страницу item'а через
  растянутую ссылку заголовка.

Registry URL и View code с карточки убраны — на витрине они конкурировали
с главным сценарием. Оба остались на странице item'а.

После копирования кнопка говорит **«Скопировано — вставьте агенту»**, а не
«Copied»: это единственное место, где мы объясняем сценарий, и стоит оно ноль.

Технически: над растянутой ссылкой поднимается только кнопка (`relative z-10`),
«Подробнее» остаётся визуальным аффордансом — клик по нему ловит та же
ссылка заголовка. Второй ссылки на тот же адрес в разметке нет.

## Страница item'а

Порядок сверху вниз = порядок убывания важности:

1. **Preview** — пользователь проверяет глазами, что это то самое;
2. **«Использовать с AI»** — главный блок: три шага прописью, большая кнопка
   Copy for AI, свёрнутый текст инструкции. Выделен усиленной рамкой;
3. **«Для разработчика»** — install-команда, registry URL, свёрнутый исходник.
   Мелким заголовком, визуально вторично.

Третий шаг в инструкции — «допишите своими словами, куда поставить» — это
v1-форма слота размещения. UI-пикера сценариев в v1 нет, см. v2.

Свёрнуто по умолчанию: текст промпта, исходник. Оба нужны для доверия
(«покажи, что ты мне подсовываешь»), но не должны отбирать экран у действия.

## Промпт — Product Delivery Prompt v1 (реализовано)

Генератор — `lib/copy-for-ai.ts`. Собирается только из metadata item'а,
вручную ничего не дописывается. Восемь секций:

1. **Install first — do not skip, do not recreate** — команда, registry URL,
   `Installs to` из `files[0].target`, npm- и registry-зависимости и явный
   запрет пересоздавать / подменять / переписывать под стиль проекта;
2. **What it is** — `description` + `meta.ai.summary`;
3. **How to use it** — строка импорта и сниппет, если есть `meta.ai.export`
   и `meta.ai.usage`; иначе — объяснение по `kind` и указание прочитать
   установленный файл;
4. **Where to place it** — текст по `kind` + строка `Placement: ___`;
5. **Keep exactly as installed** — `meta.ai.preserve`;
6. **You may change** — `meta.ai.adapt`;
7. **Rules** — `meta.ai.notes`;
8. **Verify** — рендерится, нет ошибок в консоли, совпадает с preview;
   если нет — тронуто что-то из секции 5.

Секции 3 и 4 — то, чем выдача мелкого компонента отличается от выдачи
секции. Блок ставится один раз как секция страницы и не должен попадать
внутрь узкого inline-контейнера; компонент ставится ровно туда, куда
попросил пользователь, и заменяет собой существующий контрол, а не
добавляется вторым.

Строка `Placement: ___` — v1-форма слота размещения. Пользователь дописывает
её своими словами уже в чате агента; если строка осталась пустой, промпт
велит агенту спросить, а не угадывать. UI-пикера сценариев в v1 нет.

Контракт генератора: `buildCopyForAiPrompt(item, { installCommand,
registryUrl, kind })`. `kind` приходит от вызывающего (`getItemKind`),
поэтому сам генератор не зависит от реестра.

### export и usage

Два авторских поля в `meta.ai`, оба опциональны в типе:

| Поле     | block       | component                 |
| -------- | ----------- | ------------------------- |
| `export` | опционально | обязательно по соглашению |
| `usage`  | опционально | обязательно по соглашению |

Типом это не выражено намеренно: иначе пришлось бы прямо сейчас
переписывать metadata всех пяти существующих блоков. Для секции агент и
без сниппета справится — она ставится целиком, и генератор явно велит
прочитать установленный файл. Для мелкого компонента без `usage` агент не
знает, с какими пропсами его вставлять, поэтому у первого же
`registry/components/*` эти поля обязаны быть заполнены.

Список пропсов **не хранить**: он в установленном файле, агент его прочитает.
Дублировать значит гарантировать дрейф.

Всё остальное выводимое и в `registry.json` не пишется: install-команда
(`REGISTRY_BASE_URL` + `name`), путь установки и импорта (`files[0].target`),
`kind` и `group` (реестр и категория), секции «Where to place it» и «Verify».

Общая инструкция «установи из registry, не пересоздавай» живёт **только**
в секции 1 генератора. Из `meta.ai.notes` всех пяти блоков одноимённая
строка удалена: она была скопирована в каждый item и дублировала то, что
промпт теперь говорит сам.

## Режимы превью (реализовано)

Превью выбирается по `kind` — это было условием того, чтобы мелкие
компоненты вообще можно было показывать: секционный масштаб `≈0.26`
превратил бы кнопку в нечитаемую точку около 40px.

| Место                    | `kind: block`                              | `kind: component`                          |
| ------------------------ | ------------------------------------------ | ------------------------------------------ |
| Миниатюра карточки       | рендер в 1280px + `.block-thumbnail-scale` | натуральная величина, центр кадра, паддинг |
| Фрейм на странице item'а | 760px                                      | 320px                                      |

Кадр миниатюры в обоих режимах держит пропорцию 16/9, поэтому сетка каталога
не прыгает. `/preview/[slug]` центрирует компонент и оставляет секцию как
была. Решает `components/catalog/catalog-thumbnail.tsx` (kind берётся из
`getItemKind`), `compact` у `BlockPreview` и ветка в `app/preview/[slug]`.

Подложка миниатюры компонента — **светлая нейтральная** (`--shell-surface`),
а не тёмная. Проверено на наборе кнопок: «тихая» и текстовая кнопки
рассчитаны на светлую поверхность, и на тёмном фоне их подпись почти не
читается. Светлая подложка честнее показывает компонент в той среде, для
которой он сделан, а плотные и цветные кнопки на ней тоже читаются.
Блоки подложку не меняют: у секции есть собственный фон.
