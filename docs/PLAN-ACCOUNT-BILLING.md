Рабочий план Phase 5. Заменяет строку «Payments — вне текущего scope» в

Решения, принятые заказчиком 08.09.2026:

| Развилка | Решение |
| --- | --- |
| Что продаём | Pro-компоненты по подписке: превью видно всем, установка и Copy for AI — по подписке |
| Юрлицо | Самозанятый |

## 1. Что меняется в продукте

Каталог остаётся открытым: превью, поиск, страницы item'ов видны без
регистрации — это витрина, она и продаёт. Платным становится **получение
исходника**: команда установки, файл по прямой ссылке и Copy for AI для
item'ов с меткой Pro.

Три состояния пользователя:

| | Аноним | Free (вошёл) | Pro |
| --- | --- | --- | --- |
| Каталог, превью, поиск | да | да | да |
| Copy for AI и установка Free-item'ов | 10 в месяц | 100 в месяц | без лимита |
| Установка Pro-item'ов | нет | нет | да |
| Copy for AI для Pro | нет | нет | да |
| Избранное, история | нет | да | да |
| Персональный registry-токен | нет | нет | да |
| Реферальная ссылка | нет | да | да |

Лимит — это лестница, а не забор. Аноним успевает попробовать и убедиться,
что компоненты настоящие; на одиннадцатом его просят завести бесплатный
аккаунт; сотня в месяц покрывает реальную работу над проектом, и упирается
в неё тот, кто уже получил пользу. Free-аккаунт нужен и сам по себе:
избранное и история — повод вернуться.

### Что считается копированием

Единица списания — **уникальный item за календарный месяц**. Повторное
копирование того же компонента в том же месяце не списывает ничего: иначе
человек начинает бояться нажимать кнопку и перестаёт пользоваться витриной.
Формулировка для интерфейса — «100 разных компонентов в месяц».

Счётчик обнуляется первого числа. Списание происходит при получении
исходника: нажатие Copy for AI, открытие `/f/<name>.tsx`, запрос registry —
все три канала считаются одинаково, иначе лимит обходится вторым каналом.

Для анонимов счётчик живёт в куке и подпирается IP: он обходится очисткой
куки, и это нормально — задача не поймать, а мягко подвести к регистрации.
Для вошедших счёт ведётся в базе и обойти его нельзя.

## 2. Главная техническая задача: как закрыть Pro

Обещание VibeUI — установка настоящего компонента через shadcn CLI. CLI
ходит по URL и не носит куки сессии, поэтому «закрыть страницу авторизацией»
недостаточно. Разбираем по каналам раздачи.

### 2.1. Registry (`/r/<name>.json`)

Сейчас это **статика**: `npm run registry:build` кладёт 1765 файлов в
`public/r/`, nginx отдаёт их всем. Для Pro так нельзя.

Решение — namespaced registries из shadcn CLI 3.0: пользователь один раз
прописывает namespace в своём `components.json`, токен подставляется из
переменной окружения ([Authentication](https://ui.shadcn.com/docs/registry/authentication),
[Namespaces](https://ui.shadcn.com/docs/registry/namespace)):

```json
{
  "registries": {
    "@vibeui": {
      "url": "https://vibeui.ru/r/pro/{name}.json",
      "headers": { "Authorization": "Bearer ${VIBEUI_TOKEN}" }
    }
  }
}
```

Дальше установка выглядит как `npx shadcn@latest add @vibeui/hero-021`, а
токен лежит в `.env.local` и не уезжает в git.

Что делаем у себя:

- Pro-item'ы **не попадают** в `public/r/` — `registry:build` их пропускает;
- добавляется route handler `app/r/pro/[name]/route.ts`: читает
  `Authorization`, сверяет токен, проверяет активную подписку, отдаёт тот же
  JSON, что и для Free-item'ов;
- ответы без подписки — `401` с человекочитаемым текстом и ссылкой на тариф:
  в терминале это единственное, что увидит покупатель;
- rate limit по токену (запросов в минуту) и `lastUsedAt` для диагностики.

Запасной путь для тех, кто не хочет править `components.json`, — тот же URL
с ключом в query (`?key=…`). Держим как второй вариант: ключ светится в
истории shell и в логах nginx, поэтому предлагаем его вторым.

### 2.2. Прямая ссылка на файл (`/f/<name>.tsx`)

Сейчас статический route handler с `generateStaticParams()` по всему
каталогу. Pro-item'ы убираем из `generateStaticParams`, для них тот же роут
проверяет сессию или токен.

### 2.3. Copy for AI (`/c/<slug>`)

Страница отдаёт промпт с полным описанием. Для Pro-item'а без подписки
отдаём укороченную версию: что это за компонент и как его купить.

### 2.4. Превью — источник утечки, о котором легко забыть

Превью рендерит **тот самый файл**, который получает покупатель (это
принцип проекта — один source of truth). Значит для клиентского компонента
исходник уезжает в JS-бандл браузера, и его достаёт любой человек с
DevTools. Платить за то, что лежит в бандле, никто не станет.

Что делаем:

- Pro-item'ы по умолчанию **серверные**: CSS-анимации и разметка рендерятся
  в RSC, в браузер уходит HTML, а не исходник. Большая часть каталога такая
  уже сейчас;
- если Pro-item обязан быть клиентским (`"use client"`), анониму и Free
  показываем записанный кадр — WebP или короткое видео, а живой рендер
  включаем при активной подписке;
- в чек-листе нового Pro-item'а появляется пункт «проверено: исходника нет
  в бандле страницы».

Полностью защиты не бывает: купивший может выложить файл куда угодно. Мы
защищаем от бесплатного самообслуживания, а не от копирования — как и все
подобные библиотеки.

## 3. Архитектура

### 3.1. Хранилище

PostgreSQL 16 на том же VPS (Debian 12, 2 ядра, 2.9 ГБ, сервер общий с
другими проектами). Данные пользователей остаются в РФ — этого требует
152-ФЗ, и переезд на российский сервер уже сделан.

Ограничения памяти прописываем явно: `shared_buffers 256MB`,
`max_connections 40`, чтобы база не отобрала память у соседних сайтов.
Приложение ходит через пул на 10 соединений — Next standalone работает
одним процессом.

Бэкап: `pg_dump` по systemd-таймеру раз в сутки, семь копий на сервере плюс
выгрузка в S3-совместимое хранилище. Проверка восстановления — руками, один
раз при запуске и потом раз в квартал.

### 3.2. Слой данных

Drizzle ORM: генерирует SQL-миграции файлами, не тащит бинарный движок и
не съедает память на слабой машине. Миграции применяются шагом деплоя в
GitHub Actions **до** переключения симлинка релиза.

Схема (сверх таблиц, которые заводит Better Auth — `user`, `session`,
`account`, `verification`):

```
subscription
  id, user_id, plan, status, current_period_end, cancel_at_period_end,
  payment_method_id, created_at, updated_at
payment
  id, user_id, subscription_id, yookassa_id, amount, currency, status,
  paid_at, receipt_status, payload
registry_token
  id, user_id, token_hash, prefix, created_at, last_used_at, revoked_at
webhook_event
  id (идентификатор события ЮKassa), type, received_at, processed_at, payload
favorite
  user_id, item_name, created_at
usage
  user_id, period (YYYY-MM), item_name, first_used_at
referral
  code, user_id, created_at
referral_visit
  code, visitor_id, landed_at
referral_reward
  id, inviter_id, invited_id, payment_id, days_granted, granted_at
```

`usage` хранит строку на пару «месяц + item»: остаток считается как
`100 − count(*)`, а повторное копирование того же компонента не создаёт
новой строки. Старые периоды чистятся раз в месяц тем же таймером, что
делает бэкап.

`status` подписки: `active`, `past_due`, `canceled`, `expired`. Право на
Pro считается одной функцией от подписки — отдельной таблицы прав не
заводим, дублирование состояния здесь дороже, чем join.

`webhook_event` существует ради идемпотентности: ЮKassa повторяет доставку,
пока не получит `200`, и один платёж не должен продлевать подписку дважды.

Токен registry хранится хешем (SHA-256), в интерфейсе показывается один раз
после создания. `prefix` (первые 8 символов) нужен, чтобы человек узнал свой
токен в списке.

### 3.3. Аутентификация

[Better Auth](https://www.better-auth.com) с адаптером Drizzle: email +
пароль, сессии в БД (а не только в куке — это даёт «выйти на всех
устройствах»), встроенные верификация почты, сброс пароля и rate limit.
Связка Better Auth + Drizzle + Postgres на Next 16 — типовая
([стартер](https://github.com/zexahq/better-auth-starter)), писать своё не
нужно.

Обязательные к настройке места:

- пароль ≥ 10 символов, проверка на утёкшие пароли не нужна, но верхнюю
  границу длины ставим, иначе bcrypt на длинной строке — вектор нагрузки;
- вход и восстановление — с ограничением попыток по IP и по адресу почты;
- письма верификации и сброса живут 30 минут, ссылка одноразовая;
- сессия 30 дней, продление скользящее, при смене пароля — сброс всех
  сессий, кроме текущей;
- обязательно `secure`, `httpOnly`, `sameSite=lax` на куке.

### 3.4. Почта

Отправляем с домена сайта. Чтобы письма доходили, нужен полный набор:
`SPF`, `DKIM` (ключ 2048), `DMARC` (начать с `p=none`, потом `quarantine`),
`PTR` на IP сервера и корректный `HELO`.

Здесь важно трезво оценить риск: письма верификации и сброса — критичный
путь. Свежий IP без репутации попадает в спам у Mail.ru и Gmail — не всегда,
но достаточно часто, чтобы человек не смог войти. Поэтому:

- поднимаем свой Postfix с DKIM на `vibeui.ru`;
- **сразу** закладываем возможность отправлять через SMTP-релей с того же
  домена: в коде — один интерфейс `sendMail`, провайдер меняется
  переменной окружения;
- после запуска смотрим на долю доставленных писем в постмастерах Mail.ru и
  Яндекса; если она проседает, переключаемся на релей без правки кода.

### 3.5. Платежи (ЮKassa)

[ЮKassa для самозанятых](https://yookassa.ru/platezhi-dlya-samozanyatyh/)
принимает карты, СБП и кошельки, работает без абонентской платы и
поддерживает регулярные списания.

Схема первого платежа:

1. кабинет создаёт платёж через Checkout API с `save_payment_method: true`
   и заголовком `Idempotence-Key` (UUID запроса);
2. пользователь уходит на страницу подтверждения ЮKassa;
3. ЮKassa шлёт вебхук `payment.succeeded` на наш `/api/payments/webhook`;
4. обработчик проверяет, что события с таким id ещё не было, записывает
   `payment`, создаёт или продлевает `subscription`, сохраняет
   `payment_method_id` для будущих списаний;
5. пользователь возвращается на страницу подписки, где уже активен Pro.

Автопродление: systemd-таймер раз в час дёргает защищённый endpoint, тот
выбирает подписки с истекающим периодом и делает списание по сохранённому
`payment_method_id`. Неудача — статус `past_due`, три попытки с
нарастающим интервалом, письмо пользователю, затем `expired`.

Требования к обработчику вебхука, каждое из которых обязательно:

- проверка, что запрос пришёл от ЮKassa (диапазоны IP из документации);
- идемпотентность по id события;
- ответ `200` быстро, тяжёлую работу — в ту же транзакцию, но без внешних
  вызовов;
- полный `payload` в БД: при разборе спорной оплаты это единственный
  источник правды.

Чеки. Самозанятый обязан выдать чек НПД. ЮKassa умеет формировать их
автоматически через интеграцию с «Мой налог» — это подключается в личном
кабинете ЮKassa и снимает с нас ручную работу. **Проверить при подключении**
и, если автоматической выдачи в нашем случае нет, добавить шаг: чек
формируется в «Мой налог» и ссылка отправляется письмом.

Отмена подписки: пользователь нажимает «Отменить» — ставим
`cancel_at_period_end`, доступ живёт до конца оплаченного периода. Возврат
по заявлению — вручную через кабинет ЮKassa, в интерфейсе не нужен.

### 3.6. Партнёрская программа

Реферальные ссылки есть только у **партнёров** — блогеров, которых
приглашает администратор. Бонусных дней за приглашения нет: реферал получает
ровно купленную подписку, блогер — долю от оплаты, которая считается вне сайта
по аналитике (процент не зафиксирован, в базе не хранится).

- админ в `/account/admin/partners` вводит имя блогера → одноразовая ссылка
  `vibeui.ru/i/<код>` (`partner_invite`);
- кто зарегистрировался по ней, становится партнёром (`claimed_by`) и сразу
  получает свой код (`referral`) и ссылку того же вида;
- переход по любой из ссылок кладёт код в куку на 60 дней и ведёт на главную;
- регистрация по коду партнёра ставит `user.invited_by` навсегда; по занятому
  приглашению или чужому коду — обычная регистрация;
- админ видит по каждому блогеру: зарегистрировался ли, переходы, список
  рефералов с подпиской и суммой платежей;
- партнёр в `/account/referrals` видит ссылку, счётчики и список рефералов с
  замаскированной почтой и статусом «оплатил / не оплачивал». Остальным раздел
  не показывается, прямой заход — 404.

Подробности и история решения — [PLAN-REFERRAL-PARTNERS.md](PLAN-REFERRAL-PARTNERS.md).

## 4. Личный кабинет

Маршруты под `/account`, все динамические, закрыты middleware. Каталог
остаётся статическим — auth его не трогает.

| Страница | Содержание |
| --- | --- |
| `/account` | Статус тарифа, дата следующего списания, быстрые действия |
| `/account/subscription` | Тариф, отмена и возобновление продления |
| `/account/payments` | История платежей и ссылки на чеки из «Мой налог» (вносит администратор) |
| `/account/token` | Registry-токен: создать, показать один раз, отозвать, инструкция для `components.json` |
| `/account/favorites` | Избранные item'ы |
| `/account/referrals` | Только партнёру: ссылка, переходы, рефералы и кто из них оплатил |
| `/account/security` | Смена пароля, активные сессии, выход везде |

Остаток копирований показываем в двух местах и больше нигде: в меню
аккаунта («87 из 100 в этом месяце») и в подтверждении после копирования.
При остатке меньше десяти подпись становится заметной и ведёт на тариф.
Бейдж на каждой карточке каталога не ставим — витрина должна продавать
дизайн, а не напоминать о счётчике.

Вход и регистрация — `/signin`, `/signup`, `/reset`. Кнопка «Войти» в шапке
уже есть: сейчас она открывает модалку-заглушку «Личный кабинет скоро
появится» (`components/catalog/catalog-topbar.tsx`), её и заменяем.

Страница тарифов `/pricing` — публичная, с честным описанием, что входит в
Free и Pro.

## 5. Юридическая часть

Без этого нельзя принимать деньги:

- **оферта** — публичный договор с предметом, ценой, порядком оплаты и
  возврата, реквизитами самозанятого;
- **политика обработки персональных данных** и отдельное согласие при
  регистрации (чекбокс с ссылкой, снятый по умолчанию);
- **уведомление в Роскомнадзор** о начале обработки персональных данных —
  подаётся до начала обработки;
- хранение персональных данных на территории РФ — выполнено, сервер
  российский;
- страница «Реквизиты» с ФИО, ИНН и контактом для претензий;
- чеки НПД на каждый платёж (см. 3.5).

Тексты пишет заказчик или юрист — это не работа разработчика. Наша часть:
страницы, чекбоксы, хранение факта согласия (дата, версия документа, IP).

## 6. Этапы

Каждый этап заканчивается проверяемым результатом. Порядок важен: без
хранилища нет входа, без входа нет оплаты.

### Этап 0. Подготовка (заказчик)

Магазин в ЮKassa, доступы к API, интеграция чеков НПД, DNS-записи почты,
тексты оферты и политики.

**Готово, когда:** есть shopId и секретный ключ тестового магазина, DNS
делегирован, тексты присланы.

### Этап 1. Хранилище и слой данных

PostgreSQL на VPS, роль и база для приложения, Drizzle, первая миграция,
подключение из приложения, бэкап по таймеру, применение миграций в CI.

**Готово, когда:** миграция применяется деплоем, приложение читает и пишет
в базу на проде, `pg_dump` кладёт архив по расписанию, восстановление из
архива проверено на копии.

### Этап 2. Аутентификация

Better Auth, схема пользователей, регистрация с подтверждением почты, вход,
выход, сброс пароля, rate limit, письма через свой SMTP.

**Готово, когда:** новый человек регистрируется, получает письмо, входит,
меняет пароль и восстанавливает доступ — всё на проде, с реальной почтой на
Mail.ru, Яндексе и Gmail.

### Этап 3. Кабинет, Free-аккаунт и лимит копирований

Страницы `/account`, замена модалки-заглушки, middleware, избранное,
таблица `usage`, счётчик остатка в меню и в подтверждении копирования,
кука-счётчик для анонимов.

**Готово, когда:** вошедший видит свой профиль и остаток, добавляет item в
избранное и находит его после перезахода; повторное копирование того же
item'а остаток не тратит; на 101-м уникальном компоненте показывается
предложение тарифа; неавторизованного middleware уводит на `/signin`.

### Этап 4. Разметка Pro и защита раздачи

Поле `pro` в metadata item'а и проверка в `meta:validate`; исключение
Pro-item'ов из `public/r/` и `generateStaticParams`; защищённые роуты
registry и файла; сокращённый Copy for AI; серверный рендер Pro-превью;
метка Pro на карточке и на странице item'а.

**Готово, когда:** Pro-item недоступен анониму ни через `/r`, ни через `/f`,
ни через `/c`; его исходника нет в бандле страницы; Free-item'ы работают
ровно как раньше — установка в чистом проекте проверена.

### Этап 5. Оплата

Страница тарифов, создание платежа, возврат с подтверждения, вебхук,
таблицы платежей и подписки, выдача Pro, чек.

**Готово, когда:** тестовый платёж проходит end-to-end и выдаёт Pro;
повторная доставка вебхука не продлевает подписку дважды; чек приходит
покупателю; на проде проведён один реальный платёж на минимальную сумму.

### Этап 6. Жизненный цикл подписки

Автопродление по таймеру, `past_due` и повторные попытки, письма о списании
и неудаче, отмена и возобновление, истечение и снятие прав.

**Готово, когда:** на ускоренных сроках проверены сценарии: успешное
продление, неудачное с восстановлением, отмена с доступом до конца периода,
истечение со снятием Pro.

### Этап 7. Registry-токен и запуск

Выдача и отзыв токена, инструкция в кабинете, rate limit, страницы оферты и
политики, согласие при регистрации, уведомление РКН, мониторинг платежей.

**Готово, когда:** покупатель ставит Pro-компонент в чистом проекте по
инструкции из кабинета; отозванный токен перестаёт работать; юридические
страницы опубликованы.

### Этап 8. Реферальная программа

Код и ссылка `/i/<код>`, кука атрибуции, привязка при регистрации,
начисление дней обоим после первого платежа, защита от самоприглашения,
страница `/account/referrals`.

**Готово, когда:** переход по ссылке и регистрация связывают двоих;
тестовый платёж приглашённого начисляет дни обоим и отражается в кабинете;
попытка пригласить самого себя не начисляет ничего.

## 7. Риски

| Риск | Что делаем |
| --- | --- |
| Письма верификации уходят в спам — человек не может войти | Полный DKIM/SPF/DMARC/PTR, интерфейс `sendMail` с заменой на релей без правки кода, наблюдение в постмастерах |
| Postgres отбирает память у соседних сайтов на общем VPS | Явные лимиты `shared_buffers` и `max_connections`, пул на 10 соединений, мониторинг |
| Исходник Pro-компонента утекает через бандл превью | Pro-item'ы серверные, клиентские — только под подпиской, пункт в чек-листе item'а |
| Двойное продление из-за повторного вебхука | Таблица `webhook_event`, идемпотентность по id события |
| Потеря данных пользователей | Ежедневный `pg_dump`, копия вне сервера, проверенное восстановление |
| Автоматические чеки НПД окажутся недоступны | Проверить на этапе 0; запасной путь — чек из «Мой налог» письмом |
| Каталог перестанет быть статическим и просядет по скорости | Auth только в `/account` и защищённых роутах; страницы каталога остаются SSG |

## 8. Что меняется в существующем коде

- `components/catalog/catalog-topbar.tsx` — модалка-заглушка заменяется на
  вход и меню аккаунта;
- `scripts/registry-build` (`npm run registry:build`) — пропускает Pro-item'ы;
- `scripts/validate-meta.mjs` — проверяет поле `pro` и требования к
  Pro-item'ам;
- `app/f/[file]/route.ts` — Pro-item'ы уходят из статических параметров;
- `app/c/[slug]` — сокращённый промпт без подписки;
- `registry/meta.ts` — тип item'а получает `pro?: boolean`;
- `docs/ROADMAP.md` — Phase 5 переносится из «вне scope» в работу;
- `CLAUDE.md` — из списка «не входит» убираются auth, billing и БД,
  добавляются правила работы с ними.

## 9. Что в этот план не входит

Денежные выплаты партнёрам и авторам (нужен агентский договор и НДФЛ —
Phase 6), командные аккаунты и лицензии на организацию, купоны с лимитами
и сроком, оплата картами не из РФ, мобильное приложение, админка (управление
подписками — через SQL и кабинет ЮKassa до первой сотни платящих).

Промокоды блогеров (скидка на первый платёж, привязка платежа к партнёру)
сделаны отдельным планом — [PLAN-PROMO-CODES.md](PLAN-PROMO-CODES.md).
