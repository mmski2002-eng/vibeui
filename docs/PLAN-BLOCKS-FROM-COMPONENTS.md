# План: блоки из компонентов (пирамида компонент → блок → сценарий)

Дата: 21 сентября 2026. Статус: пилот (вариант A) выполнен 21 сентября 2026, см. «Что сделано».

## Задача

Блок — секция сайта — должен собираться из компонентов каталога, а не
дублировать их разметку. Нет нужного компонента → он появляется в
`registry/components`, потом блок. Сценарий и дальше собирается из блоков.

## Что было (обследование 21.09.2026)

- 1182 компонента, 570 блоков, 85 анимаций. `registryDependencies: []` у
  **всех** 1837 items: ни один блок не зависит ни от одного компонента.
- Валидатор (`scripts/validate-meta.mjs`, `ALLOWED_IMPORT = "react"`)
  запрещал любой импорт кроме `react` и объявленных npm-пакетов.
- Доставка читала только `files[0]` (`registry/source.server.ts`,
  `lib/registry-item.ts`): один item = один монолитный файл.
- Сценарии — не items (`registry/scenarios.ts`): плоский список items с
  ролями, источник правды — демо-страница, бриф = исходник страницы +
  команда установки на каждый item; импорты `@/registry/.../<name>/<name>`
  переписываются в `@/components/vibeui/<name>` (`agentSource`).
  Композиция «компонент внутри блока» уже есть, но живёт в демо сценария
  (фотограф: `Sketch001` внутри `Sketch007` через `children`), не в блоке.
- Тема совместима: `accent` у 960/1182 компонентов и 569/570 блоков.

## Решение: вариант A — `registryDependencies`

Блок импортирует компонент прямо из реестра сайта и объявляет зависимость
в metadata:

```ts
import { Accordion001 } from "@/registry/components/accordion/accordion-001/accordion-001"
```

```json
"registryDependencies": ["accordion-001"]
```

Почему не multi-file item (вариант B): дублировал бы файл компонента в
каждом блоке-JSON, ломал правило «один item = один файл», и `shadcn build`
с путями `../../components/...` не проверен.

Пирамида получается однородной: на каждом уровне композиция — это код
верхнего уровня, части снизу ставятся своими командами. Сценарий не
меняется.

### Как доставляется

- `/r/pro/<block>.json` (`lib/registry-item.ts`): импорты в `files[].content`
  переписываются в `@/components/vibeui/<dep>`, `registryDependencies` —
  в подписанные URL `/r/pro/<dep>.json?exp&sig`. Голые имена shadcn CLI
  резолвит в ui.shadcn.com, поэтому только URL. Подпись зависимостей
  рождается на сервере при выдаче блока: валидная подпись блока (или
  ключ/подписка) и есть авторизация на его части.
- `public/r/<block>.json` (free, `scripts/strip-preview.mjs`): те же
  переписывания, зависимости — абсолютные URL `<homepage>/r/<dep>.json`.
- `/f/<block>.tsx` и панель «Исходник»: тот же переписанный файл — человек
  видит ровно то, что установится.
- Лимит копий считается один раз — за блок; зависимости по подписи не
  считаются.
- Превью не трогается: alias `@/*` резолвит `@/registry/...`.

### Правила составного блока (валидатор)

- Импорт `@/registry/<kind>/<cat>/<name>/<name>` разрешён только если
  `<name>` есть в `registryDependencies`, и наоборот: каждая объявленная
  зависимость должна импортироваться.
- Зависеть могут блок и компонент. Зависимость — компонент или анимация.
  От блока не зависит никто. (Компонент → компонент разрешён с 22.09.2026:
  карточка отзыва ставит `avatar-001`.)
- Free-блок не может зависеть от pro-компонента: иначе `public/r` раздаёт
  подписку даром. Pro-блок на free-компонентах — можно.
- Блок **не перекрашивает компонент CSS-ом** — только пропсами
  (`accent`, `background`, `tone`). Палитра `--vibeui-<dep>-*` остаётся
  у компонента, иначе блок сломается при правке компонента.
- Компонент остаётся строго self-contained (`react` only).

### Пилот

`faq-024`: заголовок + `Badge001` (eyebrow) + `Button016` («задать вопрос»)
+ `Accordion001` (вопросы). Три зависимых компонента, все серверные, все
принимают `accent`. Правило: всё интерактивное (кнопки, ссылки-кнопки,
поля, списки) — компонент каталога; заголовок и абзац остаются в блоке.

Проверка: `meta:validate` → превью и страница item'а → `/r/pro/faq-024.json`
с URL-зависимостями и переписанными импортами → слепой
`npx shadcn@latest add <url>` в пустой проект → все три файла на месте,
импорты резолвятся.

### Что менять

| Файл | Правка |
| --- | --- |
| `scripts/validate-meta.mjs` | правила выше |
| `registry/source.server.ts` | `rewriteRegistryImports`, `getDeliverableSource` |
| `lib/registry-item.ts` | deliverable source, deps → подписанные URL |
| `app/f/[file]/route.ts`, `app/api/registry-source/route.ts` | deliverable source |
| `scripts/strip-preview.mjs` | free: deps → абсолютные URL, импорты |
| `lib/copy-for-ai.ts`, `lib/i18n-prompt.ts` | строка «ставит также» в брифе |
| страница item'а | «Составлен из» со ссылками |

## Что сделано (пилот, 21.09.2026)

- Валидатор: правила составного блока (импорт ↔ `registryDependencies`,
  только блок → компонент/анимация, free-блок без pro-частей). Негативный
  тест: недообъявленная зависимость роняет `meta:validate`.
- Доставка: `getDeliverableSource` переписывает импорты; `/r/pro/<name>.json`
  отдаёт `registryDependencies` подписанными URL; `/f/<name>.tsx` и панель
  «Исходник» показывают переписанный файл; `public/r` — абсолютные URL.
- Бриф `/c/<name>`: строка «вместе с ним ставит…», curl-строки на части.
- Страница item'а: секция «Собран из» со ссылками на части.
- `faq-024` = `badge-001` + `button-016` («задать вопрос») + `accordion-001`. Текстовые
  части (заголовок, подводка) остаются в блоке: отдельный компонент под абзац не нужен. Превью, страница item'а, mobile —
  глазами. Слепой `npx shadcn@latest add <signed url>` в пустой проект:
  создано 4 файла, импорты `@/components/vibeui/*`, тела частей побайтово
  равны реестру.

### Правило на будущее

Вырезать в каталог стоит вещь, которая (1) имеет собственный рисунок —

наружу (`setX` в пропсах — стоп-сигнал), (3) не повторяет уже
существующий компонент с точностью до цвета и подписи. Иначе разметка
остаётся в блоке.

### Инструмент `carve.py`

Скрипт вырезания (scratchpad, не в репозитории): корень по `data-part`,
поля из `item.x` объемлющего `map`, типы из типа элемента, дефолты из
`DEFAULT_*`/списка по умолчанию, внешние пропсы блока — по употреблению.
Режимы, появившиеся на второй фазе:

- `--helper=Tile` — корень живёт в хелпере уровня модуля (плитки layout,
  `Sticker`, `Region`, `Review`, `Receipt`): тело хелпера до `return`
  переезжает в компонент (хуки → `"use client"` и импорт), параметры-объекты
  расплющиваются в пропсы (`texts.statusLabels` → `statusLabels`), локальные
  с именем поля переименовываются (`status` → `statusValue`).
- `--pass="name:type = default;…"` — локальные блока (state, сеттеры,
  вычисленные значения) становятся пропсами; вызов передаёт `name={name}`.
- `--autopass` — то же с выводом типов из объявления: `useState<T>`,
  стрелки/функции (сигнатура из кода, возврат по телу), `reduce` → number,
  `??`/тернар → тип правого операнда/`typeof CONST`, вызов функции с
  аннотацией → её тип. Так собраны панели data-grid.
- `--item=name` (элемент без `map`, деструктуризация), `--nth=N` (второе
  вхождение корня, первое — статичный «все»), `--ignore=a,b`, `--reuse`,
  `--minw` (12rem для абсолютных карточек — теперь только по флагу).
- Повторы корня: одно выражение `{allLabel}` → проп; статичные повторы с
  той же разметкой — позиционное сопоставление выражений
  (`{appStoreLabel}` ↔ `{playLabel}`); атрибуты с локальными блока
  (`aria-pressed`, `onClick`) уходят на вызов и у повторов.
- CSS: `@supports` как `@media`; правило «сам корень» под заголовком
  выбрасывается только для `@container`; списки селекторов делятся
  по-селекторно; предок-атрибут на корне (`[data-area="lead"]`,
  `[data-numbers]` блока с булевым пропом) сворачивается в корень
  компонента; правила с состоянием на предке блока остаются в блоке и идут
  через корень компонента: `[side] [data-vibeui-block="card-068"] [rows]`.
- Переменные, которые блок пишет из JS (`setProperty`) или задаёт снаружи
  (`--…-i` в style вызова, `--…-t` на предке), компонент читает под именем
  блока — переименование сломало бы наследование.
- Хелперы модуля тянутся с зависимостями (константы, иконки) и в нужном
  порядке; из блока убираются, если больше не используются.

### Валидатор

- Компонент может зависеть от компонента (`card-027` → `avatar-001`);
  от блока — никто.
- Явный дотяг блока до части компонента через его корень
  (`[data-vibeui-block="card-068"] [data-part="rows"]`) — не коллизия
  частей: состояние живёт на предке в блоке (свёрнутый сайдбар), часть —
  в компоненте.
- Правило для собственного корня внутри `@container` ловится только когда
  корень — единственный селектор; `[side] [data-vibeui-block="card-066"]{…}`
  — потомок, это можно.

### Оговорки

- Типы пропсов из `--autopass` (панели data-grid) выведены эвристикой;
  локально `tsc` не гоняется — расхождения покажет CI.
- Компоненты с `display:contents` (строка Ганта, шаг конвейера) сами по
  себе высоты не имеют — раскладку даёт сетка блока.
- Превью компонента строится на дефолтах из данных блока; у пропсов-функций
  дефолты-заглушки (`() => {}`), у объектов — `{} as T`.
- Один визуальный компромисс: rss-ссылка footer-028 стала строкой списка
  (`∿ rss-лента`) вместо отдельной части.

## Ревизия контролов (правило)

После сборки блока контролы пересматриваются по смыслу, не по числу:

- убрать то, что больше ничего не крутит (`ink` без части, принимающей
  его; `idPrefix`, `id`, `name` — техника, не дизайн) и тексты второго
  плана (`restLabel`, `allLabel`, `description`);
- пробросить ручки частей, меняющие вид секции: `marker`, `openFirst`,
  `numbered`/`columns`, `buttonTone`, `tint` плашки, `showTopic`;
- оставить один-два видимых текста (`title`, подпись кнопки/плашки) и тему
  целиком (`tone`, `accent`, `background`, `ink` там, где он уходит частям);
- в шапке карточки ≤5 значков. FAQ пройдены 21.09.2026 (`knobs.py`).

## Что не делаем

- Не переписываем блоки с нуля: составными они стали вырезанием своих же
  частей (см. «Добить до конца»), рисунок и поведение прежние.
- Не заводим namespace-реестр `@vibeui/*`: подписанные URL уже работают.
