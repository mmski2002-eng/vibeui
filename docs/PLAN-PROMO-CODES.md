# План: промокоды блогеров

Статус: реализовано 16.09.2026 (миграция `drizzle/0007_promo.sql`,
`lib/promo.ts`, поле на тарифах, админка, кабинет партнёра). Проверка на
проде: тестовый платёж с промокодом, см. «Порядок», шаг 2.

Цель: блогер рекламирует VibeUI, зритель вводит его ник при оплате и получает
скидку, платёж привязывается к блогеру — по этой привязке потом считается его
доля дохода. Сами выплаты в план не входят (Phase 6, нужен договор и НДФЛ):
здесь только учёт, чтобы сумму было из чего считать.

| Часть | Где | Состояние |
| --- | --- | --- |

| Партнёр = тот, кто занял приглашение (`claimed_by`), у него свой код `referral` и ссылка того же вида | `referral`, `claimInvite`, `partnerCode` | готово |

| Аналитика блогера у админа: переходы, регистрации, оплатившие, воронка | `/account/admin/partners/[id]`, `partnerStats` | готово |
| Кабинет партнёра: ссылка, счётчики, список рефералов с маской почты | `/account/referrals` | готово |
| Оплата: разовый платёж ЮKassa, цена считается на сервере, `metadata: { userId, plan }`, вебхук пишет `payment` и продлевает `subscription` | `lib/payment-actions.ts`, `lib/yookassa.ts`, `lib/payment-apply.ts` | готово |
| Цены тарифов с переопределением админом через таблицу `setting` | `lib/plan-prices.ts`, `setPlanPrices` | готово |

Важно для дизайна: автопродления нет. `app/api/payments/renew/route.ts`
только закрывает истёкшие подписки; каждый следующий месяц человек платит
руками той же кнопкой. Значит «скидка на платёж» и «скидка на подписку» —
одно и то же, и решать про первый платёж или все нужно явно (см. решения).

## Что нужно

1. У каждого партнёра — промокод: его ник. Один код на партнёра.
2. На тарифах поле «Промокод»: ввёл → видит новую цену до перехода в кассу.
3. Скидка считается на сервере и уходит в ЮKassa уже в сумме платежа.
4. Платёж помнит код, партнёра, процент и цену без скидки.
5. Партнёр видит в кабинете свой код, число оплат по нему и сумму.
6. Админ задаёт код и процент блогеру, видит оплаты по коду, может выключить код.
7. Скидка по умолчанию одна на всех, настраивается админом; у блогера можно
   переопределить.

## Решения (согласованы 16.09.2026)

| Вопрос | Решение | Почему |
| --- | --- | --- |
| Процент по умолчанию | **30 %**, ключ `promo.percent` в `setting` | как цены: правится из админки без деплоя |
| Округление | цена после скидки прилипает к «…90»: `round(цена × (1 − p) / 100) × 100 − 10` | от 690 ни один целый процент не даёт круглой цены; витрина вся на «…90» |
| Скидка на какие платежи | **только на первый**: у пользователя нет ни одного `succeeded`-платежа | вводная скидка блогера, дальше полная цена |
| На какие тарифы | Pro месяц и год, Энтерпрайз — тот же процент | считается от той же цены |
| Что с `invited_by`, если человек пришёл без ссылки, а код ввёл | ставим `invited_by`, если пусто; если уже стоит другой партнёр — не трогаем | привязка регистрации остаётся историей; доля считается по платежу |
| По чему считать долю блогера | по `payment.partner_id`, не по `invited_by` | один источник: кто дал скидку на этот платёж, тому и доля |
| Свой код самому себе | запрещено | иначе партнёр покупает себе Pro со скидкой и «долей» |
| Формат кода | ник: латиница, цифры, `-`, `_`, 3–24 символа, регистр не важен, хранится в нижнем | вводить с телефона и с голоса; `IvanBlog` и `ivanblog` — одно |
| Срок, лимит использований | нет | купоны с лимитами — другая задача; код живёт, пока партнёр в программе |
| Ссылка блогера подставляет код сама | да: `/i/<код>` уже ставит куку, на тарифах из неё берём партнёра и его промокод | блогеру достаточно одной ссылки; код — для тех, кто пришёл ногами |

Цены при 30 % с округлением до «…90»:

| Тариф | Цена | Со скидкой | Реально |
| --- | --- | --- | --- |
| Pro месяц | 690 | **490** | 29,0 % |
| Pro год | 5900 | **4090** | 30,7 % |
| Энтерпрайз месяц | 1380 | **990** | 28,3 % |
| Энтерпрайз год | 11800 | **8290** | 29,7 % |

Оговорка: на месяце «красивые» точки только 590 и 490, поэтому проценты
от 25 до 35 дают одну цену 490. Для года и энтерпрайза шаг мелкий.

## Схема данных

Второй источник правды о партнёре не заводим: код живёт в `partner_invite`,
как и сам признак партнёра.

```
partner_invite
  + promo_code       text unique null   -- ник, нижний регистр
  + promo_percent    integer null       -- переопределение; null → promo.percent
  + promo_active     boolean not null default true

payment
  + list_amount      text null          -- цена без скидки, "5900.00"
  + promo_code       text null
  + promo_percent    integer null
  + partner_id       text null references user(id) on delete set null
  + index payment_partner_idx (partner_id, paid_at)

setting
  'promo.percent' = '30'
```

Миграция `drizzle/0007_promo.sql`. Существующие платежи остаются с `null`:
для них скидки не было.

## Расчёт цены

`lib/promo.ts` (server-only):

- `normalizePromo(raw)` — trim, lower, проверка формата;
- `resolvePromo(code)` → `{ partnerId, inviteId, percent } | null`:
  код найден, `promo_active`, приглашение занято (`claimed_by`), процент —
  свой или `promo.percent`;
- `applyDiscount(price, percent)` → строка `"NNNN.00"`:
  `round(price × (1 − p) / 100) × 100 − 10`, минимум 90 ₽. Одна функция и
  для витрины, и для кассы: чек совпадает с тем, что человек видел;
- `isFirstPayment(userId)` — нет ни одного `payment.status = 'succeeded'`;
- `defaultPromoPercent()` из `setting`, без базы → 30.

Скидка считается один раз в `startCheckout`, браузер шлёт только код.
Витрина цены со скидкой не считает сама: `checkPromo` возвращает готовые
цены по всем четырём тарифам, чтобы округление жило в одном месте.

## Поле промокода на тарифах

Место — карточка Pro, между ценой и списком возможностей: скидка меняет
цену, и глаз должен видеть их рядом. Энтерпрайз своего поля не получает,
цена там пересчитывается той же скидкой.

Состояния:

1. **Свёрнуто** (по умолчанию). Тихая ссылка-кнопка «Есть промокод?» под
   ценой, `text-[#f2f2f2]/60`, без рамки. Не отвлекает тех, у кого кода нет.
2. **Ввод.** По клику раскрывается строка: поле `IvanBlog` и кнопка
   «Применить», высота 40px, в стиле полей кабинета. Enter = применить.
   Раскрытие — `acc-grow-y`/fade 220ms, `prefers-reduced-motion` без движения.
3. **Проверка.** Кнопка со спиннером (`Button pending`), поле заблокировано.
4. **Применён.** Строка сворачивается в плашку: `✓ ivanblog · −30 %` и
   крестик «убрать». Цена в карточке перестраивается:

   ```
   ~~690 ₽~~   490 ₽ /мес          ← старая цена мельче, зачёркнута, серая
   −30 % по промокоду ivanblog     ← вместо строки «anchor» под ценой
   ```

   Старая цена: `text-2xl line-through text-[#f2f2f2]/45`, новая — прежние
   `text-5xl` через `AnimatedPrice`, чтобы цифры перекатились, а не
   мигнули. Бейдж «−30 %» на кнопке оплаты: «Оплатить 490 ₽ вместо 690».
   В карточке Энтерпрайз цена тоже зачёркнута и пересчитана, без плашки.
5. **Ошибка.** Поле подсвечено `--shell-danger`, подпись под ним: «Такого
   промокода нет», «Промокод отключён», «Свой промокод применить нельзя»,
   «Скидка только на первый платёж». Код остаётся в поле для правки.
6. **Уже платил.** Ссылка «Есть промокод?» не показывается вовсе: правило
   «только первый платёж» известно на сервере до рендера.

Предзаполнение: `?promo=ivanblog` в адресе и партнёр из куки `vibeui_ref`
(если у него есть активный код) — поле сразу в состоянии «применён», человек
видит скидку без действий. Код живёт в `sessionStorage` на время визита:
переключил месяц/год — скидка не слетает.

Переключатель «Помесячно / На год» и `AnimatedPrice` уже умеют менять цену
плавно, зачёркнутая цена подключается к тому же состоянию.

Компонент — `components/pages/pricing/promo-field.tsx` (client), внутри
`PlanCards`; скрытое поле `promo` в обеих формах `startCheckout`.

## Поток оплаты

1. **Тарифы.** `checkPromo(code)` (server action) → `{ percent, prices:
   { monthly, yearly, enterpriseMonthly, enterpriseYearly } }` или код
   ошибки. Клиент только показывает. Код уходит в `startCheckout` скрытым
   полем `promo`.
2. **`startCheckout`.** `resolvePromo`, отказ своего кода, `isFirstPayment`,
   `applyDiscount`, в `createCheckout` — сумма со скидкой, описание «VibeUI
   Pro · промокод ivanblog», `metadata: { userId, plan, promo, partnerId,
   percent, listAmount }`. Битый или уже неприменимый код не роняет оплату:
   платёж идёт по полной цене.
3. **Вебхук `applyPaymentEvent`.** Из `metadata` — в новые колонки
   `payment`. Если у пользователя `invited_by` пуст — ставим `partnerId`.
   Идемпотентность прежняя (`webhook_event`, `onConflictDoNothing`).

## Кабинеты

**Партнёр `/account/referrals`.** Блок «Промокод»: код крупно, кнопка
копировать, процент скидки, «Оплат по коду: N · на сумму M ₽». Список
рефералов остаётся; в строке добавить пометку «по промокоду», если у платежей
человека стоит этот код. Раздел показывается как сейчас — только партнёру.

**Админ `/account/admin/partners/[id]`.** Секция «Промокод»: поле кода,
процент (пусто = по умолчанию), переключатель «действует», кнопка сохранить —
server action `setPartnerPromo` с записью в `admin_action`. Метрики: «Оплат
по коду», «Выручка по коду», «Скидок выдано». Воронка получает четвёртый
шаг «По промокоду».

**Админ `/account/admin/partners`.** Колонка «Код» в списке; при создании
приглашения — необязательное поле «Промокод», чтобы задать ник сразу.

**Админ `/account/admin/payments`.** Колонка «Промокод» и фильтр по партнёру
(`?partner=`), суммы за период — отсюда потом считается доля.

**Админ, цены.** Рядом с `setPlanPrices` — поле «Скидка по промокоду, %».

## Порядок

Каждый шаг проверяется отдельно и остаётся рабочим без следующих.

1. **Схема и настройка.** Миграция, `promo.percent`, `lib/promo.ts` с
   расчётом. Проверка: `applyDiscount("690.00", 30) === "490.00"`,
   `applyDiscount("5900.00", 30) === "4090.00"`, `resolvePromo` на занятом и
   незанятом приглашении, `isFirstPayment` с платежом и без.
2. **Касса.** `startCheckout` с кодом, `metadata`, вебхук пишет колонки.
   Проверка: тестовый платёж в ЮKassa с кодом → в `payment` стоят код,
   партнёр, процент, `list_amount`; без кода — `null`.
3. **Тарифы.** Поле, `checkPromo`, пересчёт цен, предзаполнение из `?promo=`
   и куки. Проверка глазами на 390/1440, обе темы, неверный код.
4. **Админ.** Код и процент у партнёра, колонки и фильтр в платежах,
   процент по умолчанию в ценах. Проверка: сменил процент → на тарифах новая
   скидка без деплоя.
5. **Партнёр.** Блок промокода и счётчики в `/account/referrals`.
6. **Документация** и запись решений.

Оценка: шаги 1–2 — один вечер, 3 — вечер, 4–5 — вечер. Ничего из этого не
требует билда локально: проверяется dev-сервером и тестовым платежом на проде.

## Риски

| Риск | Что делаем |
| --- | --- |
| Сумма в кассе расходится с витриной из-за округления | одна функция `applyDiscount` и на витрине (через процент), и в кассе; рубли целые |
| Код перебирают скриптом, чтобы найти ники | ответ одинаковый «не найден», лимит частоты на `checkPromo` по IP как у `report-actions` |
| Партнёр меняет ник, старые платежи «теряются» | доля считается по `partner_id`, код в платеже — история; смена кода админом не трогает старые строки |
| Человек с чужим `invited_by` платит по другому коду | доля идёт тому, чей код на платеже; `invited_by` не перезаписываем; в админке видны оба |
| Скидка на Энтерпрайз слишком большая в рублях | процент один, но админ может поставить блогеру свой; при необходимости добавить потолок в рублях позже |

## Что не входит

Выплаты и договоры с блогерами, купоны с лимитами и сроком, промокоды не от
партнёров (маркетинговые акции), скидка на автопродление (его нет), стек
скидок (только один код на платёж).
