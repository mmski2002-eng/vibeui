# CONTROLS — настройка item'а перед выдачей

Как пользователь меняет атрибуты компонента (текст, цвет, размер) до того,
как отдать его агенту, и что при этом меняется в превью, коде и инструкции.

Статус: реализовано. Контролы объявлены у всех одиннадцати кнопок.

Где что лежит:

| Слой                     | Файл                                                        |
| ------------------------ | ----------------------------------------------------------- |
| Тип                      | `ItemControl` в `registry/meta.ts`                          |
| Разбор и санитизация     | `lib/controls.ts`                                           |
| Маршрут                  | `app/c/[slug]/route.ts` — теперь динамический, читает query |
| Ленивая карта превью     | `registry/previews.lazy.ts`                                 |
| UI                       | `components/catalog/item-configurator.tsx`                  |
| Монтирование на карточке | `components/catalog/configure-toggle.tsx`                   |
| Проверка на сборке       | `scripts/validate-meta.mjs`, `npm run meta:validate`        |

## Что это на самом деле

У нас уже есть поле `meta.ai.adapt` — список того, что агенту **разрешено**
менять. Сейчас это проза, которую читает только модель.

Контролы — тот же список, объявленный машиночитаемо. Не новая сущность,
а структурная форма уже существующей. Отсюда правило:

**Контрол может существовать только для того, что перечислено в `adapt`.
Того, что лежит в `preserve`, в контролах быть не может.**

Иначе интерфейс начнёт предлагать сломать то, что инструкция запрещает
трогать.

## Ключевое решение: настраиваются пропсы, а не исходник

Два способа сделать конфигуратор, и они несовместимы:

|               | что происходит                                                            | цена                            |
| ------------- | ------------------------------------------------------------------------- | ------------------------------- |
| **пропсы**    | превью рендерится с выбранными значениями, меняется сниппет использования | исходник остаётся тем же файлом |
| кодогенерация | из шаблона собирается новый `.tsx` под конфигурацию                       | у каждой конфигурации свой файл |

Берём первый. Кодогенерация ломает главное правило проекта: установленный
файл перестаёт быть побайтово равным тому, что лежит в реестре, `shadcn add`
раздаёт канонический файл и не знает про конфигурацию, а каждая правка
компонента с нашей стороны перестаёт доезжать до пользователя — его копия
уже форк.

Поэтому конфигуратор меняет **три вещи и не трогает четвёртую**:

1. превью — рендерится с выбранными пропсами;
2. сниппет использования в брифе `/c/<name>`;
3. сниппет в полной инструкции;
4. **исходник компонента — не меняется никогда.**

Пользователь получает тот же файл и готовую строку вставки с его значениями.

## Схема контролов

Новое поле `meta.controls` в `registry/<...>/registry.json`, рядом с
`meta.ai`. Тип — в `registry/meta.ts`.

```jsonc
"controls": [
  { "prop": "children", "label": "Текст", "type": "text", "default": "Get started", "maxLength": 40 },
  { "prop": "tone", "label": "Тон", "type": "select", "default": "solid",
    "options": ["solid", "soft", "outline"] },
  { "prop": "size", "label": "Размер", "type": "select", "default": "md",
    "options": ["sm", "md", "lg"] },
  { "prop": "accent", "label": "Акцент", "type": "color", "default": "" },
  { "prop": "loading", "label": "Загрузка", "type": "boolean", "default": false }
]
```

Типы: `text`, `select`, `color`, `boolean`, `number`. Больше не заводить, пока
не потребует конкретный компонент — типы дешевле добавить, чем убрать.

Правила:

- `prop` обязан существовать в пропсах компонента; `children` — тоже контрол;
- `default` обязан совпадать со значением по умолчанию в самом компоненте,
  иначе превью без настройки покажет не то, что даст `<Component />`;
- у каждого `kind: component` контролы обязательны по соглашению — мелкий
  компонент без них невозможно настроить, а именно за этим на него и пришли;
- у блоков контролы опциональны и должны оставаться крупными (заголовок,
  подпись, текст кнопки). Блок — не конструктор страницы.

## Как конфигурация доезжает до агента

Значения живут **в ссылке**, на сервере не хранятся:

```
https://vibeui.ru/c/button-001?tone=soft&size=lg&children=Купить
```

Маршрут `/c/[slug]` читает query, подставляет значения в сниппет:

```
Использование:
<Button001 tone="soft" size="lg">Купить</Button001>
```

Следствие: маршрут перестаёт быть полностью статическим — с query он
динамический. Для текстового ответа в килобайт это ничего не стоит.
Без параметров отдаётся тот же бриф, что и сейчас.

Кнопка на карточке копирует ссылку **с параметрами** — то есть ровно ту
конфигурацию, которую пользователь видит в превью.

## Безопасность: ссылку читает агент

Это не косметика, а главный риск фичи.

Бриф по ссылке — документ, инструкциям которого агент следует. Любой текст
из query попадает в этот документ. Значит ссылку можно скроить так, чтобы в
неё уехала посторонняя инструкция для агента — и приедет она под нашим
доменом, то есть с нашим доверием.

Обязательные меры на маршруте:

- значение принимается, только если такой `prop` объявлен в `meta.controls`;
- `select` — строго whitelist из `options`, иначе `default`;
- `color` — только `#rgb` / `#rrggbb`;
- `boolean` — только `true` / `false`; `number` — диапазон из контрола;
- `text` — обрезка по `maxLength`, вырезание переводов строк и управляющих
  символов; ничего многострочного в бриф попасть не может;
- лишние параметры игнорируются молча.

Правило одной строкой: **в бриф не попадает ни один символ, который не
прошёл через объявленный контрол.**

## Что нужно построить

| Слой      | Что делать                                                                       |
| --------- | -------------------------------------------------------------------------------- |
| Схема     | `ItemControl` в `registry/meta.ts`, поле `meta.controls`                         |
| Валидация | разбор и санитизация query по контролам — одна функция, общая для маршрута и UI  |
| UI        | клиентский компонент с состоянием, рендерит превью с пропсами и панель контролов |
| Генератор | `buildUsage(item, values)` вместо статичной строки `meta.ai.usage`               |
| Ссылка    | `getItemDocUrl(name, values)` — добавляет непустые параметры                     |

`meta.ai.usage` остаётся запасным вариантом для items без контролов.

### Цена: превью станет клиентским

Сейчас миниатюры рендерятся на сервере и JS компонентов в браузер не уходит.
Настраиваемое превью обязано быть клиентским — иначе оно не перерисуется от
состояния.

Наши компоненты к этому готовы: обычные синхронные функции без серверных
API, `<style>` внутри, ноль зависимостей. Они импортируются в клиентский
граф как есть.

Порядок величины бандла: одиннадцать кнопок — около 48 КБ исходников,
пять блоков — около 66 КБ, до gzip. Терпимо, но это плата за каждую
карточку в сетке.

Отсюда два варианта, и выбирать надо осознанно:

1. **контролы на карточке** — то, чего мы хотим: настроил и скопировал, не
   уходя с витрины. Стоит всего бандла категории;
2. **контролы на странице item'а** — бандл только одного компонента, но
   на один клик дальше.

Разумный компромисс: на карточке контролы монтируются лениво, по первому
взаимодействию; до этого стоит серверный рендер, как сейчас. Тогда витрина
остаётся дешёвой, а настройка — на месте.

## Нужна ли база данных

Нет. Ни сейчас, ни для этой фичи.

Что мы храним и где:

| Данные                 | Где                         | Почему так правильно                                                     |
| ---------------------- | --------------------------- | ------------------------------------------------------------------------ |
| Метаданные items       | `registry/**/registry.json` | Меняются только вместе с кодом, версионируются гитом, читаются на сборке |
| Исходники              | `registry/**/*.tsx`         | Единственный источник для превью, установки и `/f`                       |
| Публикуемый реестр     | `public/r/*.json`           | Артефакт сборки, чистится при каждой                                     |
| Конфигурация контролов | query-параметры ссылки      | Эфемерна, принадлежит пользователю, серверу не нужна                     |

База данных нужна ровно тогда, когда появляются данные, которые **создаёт
пользователь и которые должны пережить деплой**: аккаунты и избранное,
аналитика установок, оценки и комментарии, компоненты от сообщества. Ничего
из этого в scope нет, и заводить хранилище заранее — прямое нарушение
принципа «не создавать абстракции заранее».

Отдельно: 1700 items из `ASSORTMENT.md` статику не ломают. Ломается другое —
время сборки, когда каждый item пререндерит страницу, бриф и файл. Лечится
не базой, а переводом страниц item'ов на генерацию по запросу с кэшем.
Решать по факту, когда сборка станет заметно долгой.

Что действительно стоит починить в хранении — не место, а **дисциплину**:
`meta` растёт без проверок. `registry:validate` проверяет схему shadcn, но
не наши поля. Нужна маленькая проверка на сборке: у каждого `component`
есть `export`, `usage` или `controls`; `default` каждого контрола входит в
его `options`; `prop` каждого контрола не встречается в `preserve`.

## Порядок работ

1. `ItemControl` в типах + контролы у `button-001` — один item, чтобы
   проверить схему на живом примере;
2. санитизация query и генерация сниппета — маршрут `/c` начинает понимать
   параметры;
3. клиентское превью с панелью контролов на странице item'а;
4. проверка на сборке (пункт про дисциплину выше);
5. контролы на карточке с ленивым монтированием;
6. заполнение контролов у остальных десяти кнопок.

Пункты 1–2 дают работающую доставку с конфигурацией даже без UI: ссылку с
параметрами можно собрать руками. Это и есть проверка, что модель верна.
